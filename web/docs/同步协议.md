# 同步协议

手机 App ↔ Web 服务端（`web/server-java`）的数据同步约定。服务端已完整实现。

> **v2 起：每台设备的数据在服务端完全隔离。**
> 不同移动端设备的数据不再互相同步 —— 各设备有自己的库文件和自己的变更日志，
> 同 ID 行不会互相覆盖。详见第 2 节。

---

## 1. 设计目标与约束

| 目标 | 做法 |
| --- | --- |
| App 端改动尽量小 | 主键仍用 `AUTOINCREMENT`，不需要改成 UUID；表结构不强制加同步字段 |
| **不同设备数据互不干扰** | 每台设备一个独立目录（库 + 变更日志都在里面），服务端只在同一设备内部做同步 |
| 导出的库必须能被 App 直接导入 | 规范库保持纯 App 结构，同步元数据全部放在各设备自己的 `sync.db` |
| 网页改动能被手机感知 | 写入追加到**该设备**的 `change_log`，手机按自增 `seq` 增量拉取 |
| 冲突不静默丢数据 | 服务端保留自己的版本，冲突写入全局 `conflicts` 表（标了属于哪台设备）并在网页上可见 |
| 重复推送无副作用 | 按行内容 SHA-1 判重，内容一致时不写日志、不涨版本（已实测幂等） |

## 2. 三层数据（按设备隔离）

```
┌──────────────────────────── server/data/ ────────────────────────────┐
│                                                                      │
│  devices/phone-e3e655ac/          ← 手机 A 自己的一整套              │
│      deepseek.db / novel.db          规范库：与 App 表结构完全一致    │
│                                       （导出给 A 的就是这些文件）      │
│      sync.db                         该设备的同步元数据：             │
│                                        row_meta    行版本 / 内容哈希  │
│                                        change_log  变更流水（seq）    │
│                                                                      │
│  devices/phone-1bf2d708/          ← 手机 B 自己的一整套（同上）      │
│                                                                      │
│  devices/web-console/             ← Web 控制台自己的一整套            │
│                                                                      │
│  sync.db                          ← 全局登记表（跨设备共享）          │
│      devices          设备清单：设备号、名称、数据目录、最后活跃时间  │
│      device_cursors   每台设备的拉取水位 / 最后推送时间               │
│      conflicts        冲突留档（带 device_id）                        │
│      sync_requests    「整库同步」待办                                │
│      sync_progress    手机上报的实时进度                              │
│  usb-tunnel-state.json            ← USB 隧道守护的收尾记录（见 2.3）  │
└──────────────────────────────────────────────────────────────────────┘
```

**行身份** = `(设备, db, table, pk)`。因为**变更日志也按设备分开**，
A 手机 `push` 的行只会进 A 的 `change_log`，B 手机 `pull` 时读的是 B 自己的
`change_log`，物理上不可能看到 A 的数据。

### 2.1 「当前设备」怎么确定

| 场景 | 依据 |
| --- | --- |
| 手机同步 | 请求体 / 查询参数里的 `deviceId`（手机自己生成并持久化，例如 `phone-e3e655ac`） |
| 网页读写 | 请求头 `x-device-id`（右上角「当前设备」下拉框，默认 `web-console`） |
| 都没给 | 默认 `config.webDeviceId`（`WEB_DEVICE_ID`，默认 `web-console`） |

设备号必须在登记表里，否则返回 `404` 并列出可用设备（避免打错字就凭空建出一个空槽位）。

### 2.2 数据在设备之间怎么搬

服务端**不提供**跨设备自动合并；要搬就显式搬一次（网页上两步）：

1. 切到源设备 → 导出 `.db`
2. 切到目标设备 → 导入该 `.db`（合并模式）

### 2.3 连接通道：手机怎么找到电脑

设备隔离解决的是「数据别串」，连接通道解决的是「手机怎么连上」。手机端按可靠性逐级尝试
（`lib/features/sync/data/address_resolver.dart`）：

| 顺序 | 通道 | 说明 |
| --- | --- | --- |
| 1 | USB 隧道 `http://127.0.0.1:<port>` | 电脑上跑着 Java 服务时默认会自动建好 `adb reverse tcp:<port> tcp:<port>`，手机上的回环地址就是电脑。不看 Wi-Fi、不经过路由器、不受防火墙影响 |
| 2 | 上次用的地址 / 历史地址 | 命中率最高，一次探活就结束（最多记 6 个） |
| 3 | 热点网关 | 电脑直连手机热点、或手机开 USB 网络共享时，网关即电脑：`192.168.43.1` / `192.168.42.1` / `192.168.137.1` / `172.20.10.1`，以及本机网段的 .1/.2/.129 |
| 4 | UDP 广播自报 | 手机往 3211 端口广播一句 `deepseekapp-sync?`，服务端回一句带端口的 JSON，手机用它回包的源地址连接 |
| 5 | 扫描局域网 | 逐个 /24 网段探 `/api/health`（兜底，最慢） |

**USB 隧道这条路为什么最稳**：它走的是 adb 的 USB 通道，与网络完全无关；
隧道建立后手机访问 `127.0.0.1:<port>` 就直接落在电脑的回环口上。
电脑侧由 `web/server-java/src/main/java/com/deepseekapp/webserver/usb/AutoUsbTunnel.java` 负责建立与守护：

- 每 2 秒巡一遍已授权设备，隧道掉了自动重建（拔插数据线、adb 重启都能自愈）
- 被强制关闭时来不及清理隧道，会把设备号写进 `data/usb-tunnel-state.json`；
  下次启动、且该设备插着时先清残留再重建，避免手机连到一个已经没服务的端口
- 按 Ctrl+C 退出时顺手清理隧道

电脑侧还有 `GET /api/net` 列出这台机器上所有「手机可能连得上」的地址
（真网卡优先、虚拟网卡标为不可用），供网页/手机端提示用户该填哪个。

## 3. 主键分配（避免两端撞 ID）

| 来源 | 主键范围 | 说明 |
| --- | --- | --- |
| 手机 App | 1 ~ 999,999,999 | sqflite 的 `AUTOINCREMENT`，从 1 开始 |
| Web 端新建 | ≥ 1,000,000,000 | `syncStore.allocateWebId(deviceId, db, table)`：取该设备槽位内当前最大值与 10 亿中的较大者 |

> v2 里两台手机的同 ID 行已经不会互相影响了（各在各的槽位），
> 段位分配仍然保留：它保证同一台设备内部「网页新建」与「手机新建」不撞 ID，
> 也让导出的文件被 App 导入后不会覆盖 App 已有的小 ID 行。

## 4. 版本与冲突裁决

每行在**该设备槽位**的 `sync.db → row_meta` 里有一个 `rev`（从 1 开始）。推送时的判定规则：

| 情况 | 结果 |
| --- | --- |
| 服务端没有这一行 | 接受，`rev = 1` |
| 内容哈希与服务端一致 | **幂等忽略**，不写日志、`rev` 不变 |
| 来件 `rev` > 服务端 `rev` | 接受，`rev = 来件 rev` |
| 来件 `rev` < 服务端 `rev` | **冲突**，服务端保留，写入 `conflicts`，响应里回传服务端整行 |
| `rev` 相同但内容不同 | 按 `strategy` 裁决（见下） |

`strategy` 三个可选值（默认 `server-wins`）：

| 值 | 含义 |
| --- | --- |
| `server-wins` | 服务端版本获胜（默认，最安全） |
| `client-wins` | 客户端版本获胜 |
| `last-write-wins` | 比较 `updatedAt`（毫秒），大者获胜 |

**删除**：`op: "delete"` 时若服务端 `rev` 更高则同样记为冲突；否则硬删除该行、在 `row_meta` 留墓碑、写一条 delete 日志。
级联删除（如删会话连带删消息）由服务端负责把每一行都写进日志，手机端不会留下"幽灵子行"。

> 冲突记录进**全局** `conflicts` 表并带 `device_id`，`GET /api/sync/conflicts?device=xxx` 可只看某台设备的。

## 5. 接口定义

统一响应：成功 `{ "ok": true, "data": ... }`；失败 `{ "ok": false, "error": "说明" }`（配 HTTP 状态码）。
开启鉴权后除 `/api/health` 外都要带 `x-api-token` 请求头。
网页侧的所有业务接口还要带 `x-device-id` 指定看哪台设备（不带则默认 `web-console`）。

### 5.1 探测服务

```http
GET /api/health        （无需令牌）
→ { "ok": true, "data": { "apiVersion": 2, "serverTime": 1767258000000,
                          "authRequired": false,
                          "isolation": "per-device", "deviceCount": 2,

```

### 5.2 增量拉取（服务端 → 手机）

```http
GET /api/sync/pull?since=0&limit=500&deviceId=phone-1&db=deepseek
```

| 参数 | 说明 |
| --- | --- |
| `since` | 本地已拉取到的最大 `seq`，首次传 0 |
| `limit` | 单次最多返回多少条（默认 500，上限 2000） |
| `deviceId` | **必填**：拉取哪台设备的槽位（同时更新该设备的拉取时间） |
| `db` | 可选，只拉某个库 |

```json
{
  "ok": true,
  "data": {
    "deviceId": "phone-1",
    "changes": [
      { "seq": 12, "db": "deepseek", "table": "chat_sessions", "pk": 3,
        "op": "upsert", "rev": 4, "originDevice": "web-console",
        "serverTime": 1767258000000,
        "row": { "id": 3, "title": "标题", "create_time": "2026-01-01T10:00:00.000",
                 "last_message": "", "system_prompt": "", "summary": "" } },
      { "seq": 13, "db": "deepseek", "table": "chat_messages", "pk": 9,
        "op": "delete", "rev": 2, "originDevice": "web-console", "row": null }
    ],
    "lastSeq": 13,
    "serverSeq": 40,
    "hasMore": true
  }
}
```

客户端处理要点：

1. `op = "upsert"` → 按 `row` 整行写入本地对应表；
2. `op = "delete"` → 按 `(db, table, pk)` 删除本地行；
3. **把 `lastSeq` 存为本地游标**，下次 `since=lastSeq`。
   注意：即使 `changes` 为空也要保存，否则会永远重复拉同一段；
4. `hasMore = true` 时立刻再拉一次，直到 `false`；
5. `row` 里的主键就是本地主键，直接落库即可。

> v1 会把「自己推上去的变更」过滤掉（`originDevice === deviceId`），v2 **不再过滤**：
> 变更日志本来就只属于这一台设备，且设备自己写的行在 push 时已记账（rev + 内容指纹），
> 不会造成重复下发。

### 5.3 推送（手机 → 服务端）

```http
POST /api/sync/push
Content-Type: application/json

{
  "deviceId": "phone-1",
  "strategy": "server-wins",
  "changes": [
    { "db": "deepseek", "table": "chat_sessions", "pk": 3, "op": "upsert",
      "rev": 5, "updatedAt": 1767258000000,
      "row": { "id": 3, "title": "改过的标题", "create_time": "2026-01-01T10:00:00.000",
               "last_message": "hi", "system_prompt": "", "summary": "" } }
  ]
}
```

`row` 必须是**整行快照**（不是差量）。缺少「NOT NULL 且无默认值」的列会被拒绝并明确告知缺哪些。
推送只写进 `deviceId` 这台设备的槽位；该设备不存在时会自动登记并建好目录（首次同步即可用）。

```json
{
  "ok": true,
  "data": {
    "deviceId": "phone-1",
    "accepted": 1, "skipped": 0, "conflicts": 0, "serverSeq": 41,
    "results": [
      { "db": "deepseek", "table": "chat_sessions", "pk": 3, "op": "upsert",
        "status": "applied", "rev": 5, "seq": 41 }
    ]
  }
}
```

`status` 取值：`applied`（已写入）/ `unchanged`（内容一致，幂等跳过）/
`conflict`（被裁决为服务端获胜，响应里带 `serverRow` 供客户端覆盖本地）/ `error`（带 `message`）。

> **App 端采用「本地指纹比对」的增量推送。**
> 每行推送/拉取成功后，会把「服务端版本号 + 当时内容的指纹」记在本机
> `sync_state(rev, hash)`（hash 用 FNV-1a 64 位，不用 `Object.hash` ——
> 后者对字符串带每个 isolate 的随机种子，重启后同一个内容会算出不同结果）。
> 下次推送时先在本地比对指纹：
>
> - 指纹一致 → **这一行根本不发**，网络传输量只跟「这次改了多少」有关
> - 指纹不一致 → 按 `rev + 1` 推送
> - 簿记里有、本机表里没有 → 判定为**用户在本机删掉了**，推一条 `op: "delete"`
>
> 服务端的内容哈希判重保留作为兜底：即使客户端判重失效，重复内容也不会写库、不会涨版本。
>
> ⚠️ 升级到该版本后的**第一次同步仍会全传一遍**（本机还没有指纹基线），之后就只传改动了。
> 从 v1 升到 v2 的服务端同理：各设备槽位是新的，第一次同步会把本机数据全量推到自己的槽位。

### 6.3 同步客户端骨架

```dart
class SyncClient {
  final Dio _dio;                      // BaseOptions(baseUrl: 'http://<电脑IP>:3210')
  final String deviceId;               // 首次生成并持久化，例如 phone-a1b2c3d4e5f6

  /// 全量推送：把本地所有业务表分批推上去，服务端自动按内容去重
  Future<void> pushAll() async {
    for (final entry in _tableRegistry) {          // 表注册表：库名 + 表名 + 取数 SQL
      final rows = await _readAll(entry);
      for (final batch in _chunk(rows, 200)) {
        await _dio.post('/api/sync/push', data: {
          'deviceId': deviceId,
          'strategy': 'server-wins',
          'changes': [
            for (final r in batch)
              {
                'db': entry.db,
                'table': entry.table,
                'pk': r['id'],
                'op': 'upsert',
                'rev': await _nextRev(entry, r['id'] as int),   // sync_state.rev + 1
                'row': r,
              },
          ],
        });
      }
    }
  }

  /// 增量拉取：循环拉到 hasMore = false，每轮都保存 lastSeq
  Future<void> pullSinceLast() async {
    var since = await _kvGetInt('last_pull_seq') ?? 0;
    while (true) {
      final res = await _dio.get('/api/sync/pull', queryParameters: {
        'since': since, 'limit': 500, 'deviceId': deviceId,
      });
      final data = res.data['data'] as Map<String, dynamic>;
      await _applyChanges(data['changes'] as List);       // upsert / delete
      since = data['lastSeq'] as int;
      await _kvSetInt('last_pull_seq', since);            // 关键：空批次也要存
      if (data['hasMore'] != true) break;
    }
  }
}
```

### 6.4 需要注册进同步的表

`deepseek` 库：`chat_sessions`、`chat_messages`、`outline_records`、`outline_chapters`、
`battle_scenes`、`character_chat_sessions`、`character_chat_messages`、`character_tags`、
`world_info_entries`、`character_memories`、`trpg_campaigns`、`trpg_characters`、`trpg_messages`，
以及四张单行设置表（`user_settings` / `battle_settings` / `outline_settings` / `chapter_settings`）。

`novel` 库：7 张表全部。

⚠️ 单行设置表里的 `apiKey` / `baidu_api_key` 建议**不要**同步（网页端不需要你的密钥）。
服务端导出时会自动清空，但推送方向由 App 控制。

### 6.5 触发时机建议

| 时机 | 动作 |
| --- | --- |
| App 启动 / 手动点"同步" | `pullSinceLast()` 再 `pushAll()` |
| 退出前台前 | `pushAll()`（成本低：内容没变就是一堆 unchanged） |
| 首次连接 | 先 `pushAll()` 建立基线，再 `pullSinceLast()` |

### 6.6 连接通道（v2 追加）

App 端不再假设「用户已经填好地址」：

- `AddressResolver.resolve()` 按 2.3 的顺序逐级找电脑，返回 `(baseUrl, kind, step)`；
  `kind` 用于界面显示「USB 隧道 / 局域网 Wi-Fi / 热点 / 手动地址」。
- 命中的地址写进 `sync_kv.server_base_url`，并追加到 `sync_kv.known_base_urls`
  （最多 6 个，最近用的在前），下次优先命中。
- 解析结果在内存里缓存 45 秒，避免 5 秒一次的轮询反复走解析链；
  连接失败时清缓存，下一轮重新解析（换网 / 拔线都能自愈）。
- `handlePendingRequest()`（前台轮询）在完全没配过地址时也会先解析一次，
  所以「插上线 + 电脑上跑着 Java 服务」之后手机不用做任何配置就能被网页点名同步。
- 同步页顶部有「连接通道」面板：实时显示 USB 隧道是否就绪、当前用的是哪种通道，
  并提供「自动找电脑」与「用 USB 连」两个按钮；服务地址留空也能直接点同步。

新增的本地键（`sync_kv`）：

| 键 | 含义 |
| --- | --- |
| `server_base_url` | 上次用过的地址 |
| `known_base_urls` | 历史可用地址（换行分隔，最多 6 个） |
| `channel_kind` | 当前通道种类（`usb` / `lan` / `hotspot` / `manual`） |

## 7. 安全与运维

### 7.1 鉴权

- `server/.env` 里设置 `API_TOKEN=xxx` 后，除 `/api/health` 外全部接口要求 `x-api-token` 头；
- 前端在 `app/.env.local` 里设置 `VITE_API_TOKEN=xxx`（与服务端保持一致）；
- **只在局域网使用时可以不开**；任何公网暴露（端口映射、内网穿透）都必须开，
  否则等于把**所有设备**的数据库都公开。

### 7.2 备份

`web/server/data/` 整目录就是全部数据：

```
data/
  devices/<设备号>/deepseek.db | novel.db | sync.db
  sync.db
```

停服务后整目录复制即可（`-wal` / `-shm` 是 WAL 临时文件，不用单独备份）。

### 7.3 日志增长

每台设备自己的 `change_log` 会随写入增长。网页「同步与备份」页的
「清理本设备旧日志」按**该设备的** `device_cursors.last_pull_seq` 裁剪，
不会影响其它设备。接口是 `POST /api/sync/prune`（作用于当前 `x-device-id`）。

### 7.4 磁盘占用

每台设备都是独立库文件，设备多时占用会线性增长（空库约 100KB，
数据量取决于该设备同步了多少行）。不再需要的设备可以直接在网页上「删除数据」。

### 7.5 从 v1 升级

v1 把全部设备混在 `data/deepseek.db` / `data/novel.db` 里。首次以 v2 启动时：

| 情况 | 行为 |
| --- | --- |
| `devices` 表为空（全新装） | 自动把旧库复制进 `data/devices/web-console/`，原文件改名 `*.legacy-bak` |
| `devices` 表已有记录 | **不搬**（分不清混库属于哪台手机），启动横幅 + 网页黄色提示告知；需要时在网页上手动导入一次 |

元数据库会自动补列：`devices.scope_dir`、`conflicts.device_id`（后者按来源设备回填）。

## 8. 已知限制与升级路径

| 限制 | 说明 / 升级路径 |
| --- | --- |
| 设备之间不自动合并 | 这是 **有意为之**（不同设备数据不同步）。要合并就在网页上导出 + 导入一次 |
| 主键是整数段位而非 UUID | 段位隔离能避免同一设备内部撞 ID；跨设备已经互不影响，不再需要合并策略 |
| 没有自动后台同步 | 依赖 App 主动调用；服务端不做推送（没有长连接） |
| 删除是硬删除 | 服务端删除后本地靠墓碑 + 日志保证不复活；但没有"回收站 / 撤销" |
| 大文本整行传输 | `outline_chapters.content` 等可能是几万字，推送时按行整发；表很大时用 `limit` 与分片批处理 |
| 设备目录名做了字符过滤 | 设备号里的非 `[A-Za-z0-9._-]` 会被替换成 `_`，并记录在 `devices.scope_dir` |
