# 数据模型

Web 端与手机 App 共用同一套表结构。本文是这一套结构的说明与**维护手册**。

> 唯一权威副本：`web/server-java/src/main/resources/schema.json`
> 它同时负责：① 生成建表 SQL ② 驱动前端表格/表单 ③ 导入时的校验与告警。

---

## 1. 两个数据库，24 张表

| 数据库 | 文件 | 版本 | 表数 | 内容 |
| --- | --- | --- | --- | --- |
| 主库 | `deepseek.db` | `user_version = 33` | 17 | 智能对话、写小说、角色扮演、跑团、全局设置 |
| 小说游戏库 | `novel.db` | `user_version = 1` | 7 | 副本、角色、技能、装备、交集、剧情记录 |

版本号与 App 侧严格对应：
`lib/core/db/database_helper.dart` 的 `_dbVersion = 33`、`novel_db_helper.dart` 的 `databaseVersion = 1`。

> 除这 24 张业务表外，App 的 `deepseek.db` 里还有两张**本机专用**的同步簿记表
> `sync_state`（每行的服务端版本号）与 `sync_kv`（设备号、同步游标），
> 它们不参与同步，导出时会被服务端当作本机表忽略（见 `schema.js` 的 `LOCAL_ONLY_TABLES`）。
App 导入时会检查 `PRAGMA user_version`，所以导出文件必须写对版本号（`exporter.js` 已保证）。

## 2. 主库 deepseek.db（17 张表）

### 2.1 全局设置（单行表）

| 表 | 说明 |
| --- | --- |
| `user_settings` | id 固定为 1。模型、温度、top_p、max_tokens、上下文轮数、系统提示词、联网搜索配置（`search_engine` / `search_count` / `search_freshness` / `search_need_content` / `baidu_api_key`）、`apiKey` 等 27 列 |
| `battle_settings` | id 固定为 1。战斗场景生成的模型参数 |
| `outline_settings` | id 固定为 1。大纲生成的模型参数 + 三个检查点开关 |
| `chapter_settings` | id 固定为 1。章节写作参数 + 单章字数范围 + 剧情账本开关 |

「单行表」在网页上要按 id 编辑，**不要新增行**，否则 App 读取时行为未定义。

⚠️ 导出时 `apiKey`、`baidu_api_key` 会被清空（可用 `--keep-secrets` 或 `?sanitize=0` 保留）。

### 2.2 智能对话

| 表 | 关键字段 | 外键 |
| --- | --- | --- |
| `chat_sessions` | `id`, `title`, `create_time`, `last_message`, `system_prompt`, `summary` | — |
| `chat_messages` | `id`, `session_id`, `role`(user/assistant), `content`, `thinking_text`, `search_results`, `timestamp` | `session_id → chat_sessions.id` ON DELETE CASCADE |

`thinking_text` 存思维链，`search_results` 存联网搜索来源（JSON 字符串）。
删除会话会**级联删除**其消息，服务端会为每一行都写变更日志（见 `syncStore.removeRowCascade`）。

### 2.3 写小说

| 表 | 关键字段 | 外键 |
| --- | --- | --- |
| `outline_records` | `id`, `title`, `genre`, `theme`, `protagonist`, `worldview`, `content`(正文), `skeleton`(骨架 JSON), `foreshadows`(伏笔), `story_state`(剧情账本), `characters`(人物档案 JSON) | — |
| `outline_chapters` | `id`, `outline_id`, `event_index`, `event_type`, `event_title`, `event_summary`, `content`, `status`, `ai_summary`, `story_state` | `outline_id → outline_records.id` CASCADE |
| `battle_scenes` | `id`, `user_input`, `ai_result`, `character_skills`, `battle_scene_desc`, `battle_result`, `status` | — |

`outline_chapters.story_state` 是**每章独立的剧情账本**；`outline_records.story_state` 只是最新已完成章节的镜像。

### 2.4 角色扮演

| 表 | 关键字段 | 外键 |
| --- | --- | --- |
| `character_chat_sessions` | `id`, `character_name`, `description`, `personality`, `scenario`, `system_prompt`, `summary` | — |
| `character_chat_messages` | `id`, `session_id`, `is_user`(0/1), `content`, `timestamp` | `session_id → character_chat_sessions.id` CASCADE |
| `world_info_entries` | `id`, `session_id`, `title`, `content`, `keywords`(JSON 数组), `enabled` | `session_id → character_chat_sessions.id` CASCADE |
| `character_memories` | `id`, `session_id`, `content`, `category`, `importance` | `session_id → character_chat_sessions.id` CASCADE |
| `character_tags` | `id`, `character_name`(**UNIQUE**), `tags`(JSON 数组) | — |

`character_tags` 是按 `character_name` 唯一索引的，跟会话不是外键关系：改名字时要注意两边不同步。

### 2.5 跑团模拟器

| 表 | 关键字段 | 外键 |
| --- | --- | --- |
| `trpg_campaigns` | `id`, `name`, `dm_prompt`, `scene`, `flags`(JSON), `summary` | — |
| `trpg_characters` | `id`, `campaign_id`, `name`, `race`, `char_class`, `level`, `str`/`dex`/`con`/`intl`/`wis`/`cha`, `max_hp`, `current_hp`, `armor_bonus`, `skilled_skills`, `inventory`, `is_player` | `campaign_id → trpg_campaigns.id` CASCADE |
| `trpg_messages` | `id`, `campaign_id`, `is_user`, `content`, `meta`(JSON), `timestamp` | `campaign_id → trpg_campaigns.id` CASCADE |

⚠️ `intl` 是智力字段（不是 `int`，因为 `int` 在某些 SQL 方言里是保留字）。字段名不要"顺手改对"。

## 3. 小说游戏库 novel.db（7 张表）

```
copy_table（副本）
├─ copy_record_table.copy_id          副本的总体剧情记录
├─ char_copy_story_table.copy_id      每个角色在该副本里的单独剧情
├─ skill_table.source_copy_id         技能来源副本（可空）
└─ equipment_table.source_copy_id     装备来源副本（可空）

character_table（角色）
├─ skill_table.char_id                角色技能
├─ equipment_table.char_id            角色装备
├─ character_intersection_table       角色交集（char_a_id / char_b_id 都指向本表）
└─ char_copy_story_table.char_id      角色在副本里的单独剧情
```

| 表 | 关键字段 |
| --- | --- |
| `copy_table` | `copy_name`, `model_config`, `create_time`, `is_running`, `unread_record` |
| `character_table` | `char_name`, `base_desc`, `create_time` |
| `skill_table` | `char_id`, `skill_name`, `skill_desc`, `source_copy_id` |
| `equipment_table` | `char_id`, `equip_name`, `equip_attr`, `source_copy_id` |
| `character_intersection_table` | `char_a_id`, `char_b_id`, `intersection_desc`, `update_time` |
| `copy_record_table` | `copy_id`, `total_story`, `create_time` |
| `char_copy_story_table` | `copy_id`, `char_id`, `single_story` |

⚠️ 本库有 7 个显式索引（`idx_skill_char_id` 等），`schema.js` 已同步定义，导出时会一起带上。

## 4. 时间格式：两个库不一样！

这是最容易踩的坑：

| 数据库 | 存储方式 | 示例 | Dart 侧写法 |
| --- | --- | --- | --- |
| `deepseek.db` | **TEXT**，ISO 8601 字符串 | `2026-01-01T10:00:00.000` | `DateTime.now().toIso8601String()` |
| `novel.db` | **INTEGER**，毫秒时间戳 | `1767258000000` | `DateTime.now().millisecondsSinceEpoch` |

网页端已按列类型自动适配：ISO 字符串会格式化成 `2026-01-01 10:00:00` 显示，
毫秒时间戳在详情里直接显示数字（`novel` 库的表在 `schema.js` 里标了 `timeColumns`，需要时可用于格式化）。

**新增记录时**：`deepseek` 库的 `create_time` / `timestamp` / `created_at` / `updated_at`
如果没传，服务端会按列类型自动补当前时间（TEXT 补 ISO，INTEGER 补毫秒）。

## 5. 已知问题：`outline_settings.pause_after_minor` 缺列

排查中发现的一个 App 侧隐患，记录下来避免以后踩坑：

- `database_helper.dart` 的 `_onCreate`（第 175~186 行）建 `outline_settings` 时**没有** `pause_after_minor` 列；
- 该列只在 **V29 迁移**（第 819~826 行）里通过 `ALTER TABLE` 添加；
- 而 `outline_setting.dart` 的 `toMap()`（第 31 行）会把这个列写进 UPDATE。

**后果**：全新安装（走 `_onCreate`）的用户，第一次保存大纲设置时会因为
`no such column: pause_after_minor` 而失败；老用户（走迁移升级）不受影响。

**Web 端处理**：`schema.js` 按「升级后的完整形态」定义该列（带默认值 0），
所以网页编辑和导出都正常；导出的库比全新安装的 App 多这一列，App 能正常读取。

**已修复**（随同步功能一起改的，`database_helper.dart`）：

1. `_onCreate` 的 `outline_settings` 补上了 `pause_after_minor INTEGER NOT NULL DEFAULT 0`；
2. v33 迁移里对已存在的库做一次 `ALTER TABLE` 兜底，所以老库和新库都不会再缺列。

## 6. 如何跟随 App 升级表结构

App 改了表结构后，Web 端只需要动 `web/server-java/src/main/resources/schema.json` 一处：

1. 在对应表的 `columns` 数组里增删列（写清 `type` / `notNull` / `default` / `ref`）；
2. 更新文件顶部的 `appDbVersion`（当前 38，须与 `database_helper.dart` 的 `_dbVersion` 保持一致）；
3. 重启 `web/server-java`，确认建表、导入、导出都正常。

**复制新列时注意**：`default` 要写成**原始 SQL 字面量**，字符串必须自带引号，
例如 `default: "'text'"`、`default: "''"`、数字则写 `default: '0'`。

如果导入了一个 Web 端还没定义的库版本，接口会返回 `409` 并提示
「数据库版本 vXX 高于 Web 端支持的 vYY」——这是有意为之的护栏，避免静默丢字段。
来源库中多出来的列也会在导入报告的 `unknownColumns` 与 `warnings` 里列出来。

## 7. 校验方法

```powershell
cd web/server-java
.\mvnw.cmd spring-boot:run    # 启动后导入 / 导出一份 .db，确认建表与字段正常
```

其中几项专门盯着数据模型：
- 导入后 `chat_sessions` / `chat_messages` / `outline_chapters` / `trpg_messages` 行数正确；
- 重复导入同一份文件 → 12 行全部判定为「未变化」、水位不增长（幂等）；
- 导出文件 `user_version = 33`、恰好 17 张表、且不含 `row_meta` 等元数据表；
- `PRAGMA integrity_check = ok` 且 `PRAGMA foreign_key_check` 无违规。
