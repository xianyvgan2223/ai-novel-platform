- 基于 Spring AI `@Tool` 注解注册 **14 个工具**（数据查询 / RAG / 大纲 / 章节 / 联网搜索 / 下载 / 任务计划 / 向用户提问），自研 OpenAI 兼容流式客户端（usage、工具分片累积、首 token 前重试、取消），完成敏感列脱敏、SSRF 防护、50MB 下载上限等安全边界。
- 定位并修复联网搜索两阶段请求的前缀失配（搜索回答缓存命中恒为 0）：第二阶段从「重建历史 + 删 tools」改为「复用第一阶段消息快照 + 保留 tools + 指令约束 + 兜底重试」，真实 API 对照验证命中从 **0 → 256/416**。
- 统一写作 / 游戏类功能的提示词结构为「固定内容在前、变化内容在后」，并实现会话级 + 消息级缓存命中和 token 用量的完整展示链路，持续压低长会话成本。

## 2. 详细版（项目经历展开，STAR）

### 背景
面向个人小说创作者，把「查数据、找素材、生成大纲、写章节、联网找资料、下载素材」串成一个可以连续对话的 Agent。用户不写代码，用自然语言让 Agent 调工具完成任务；长会话可达数小时，必须解决上下文长度、成本、断线和可恢复性。

### 职责（独立完成）
Java 后端 Agent 服务 + Vue 3 控制台 + 移动端聊天侧接入，包括 run 生命周期、上下文工程、工具平台、缓存/用量、前端交互与测试。

### 关键工作

**① Agent 运行时（核心）**
- 设计 `session → message → run → event` 持久化模型（`agent_sessions / agent_messages / agent_runs / agent_tasks / agent_downloads`）；
- 事件驱动：每轮 run 通过 SSE 推送 `message / tool / task / ask / stage / download / usage / done` 等事件，带自增 `seq`，前端断线后按 `seq` 回放，不重不漏；
- 进程重启恢复：启动时扫描未完成 run，用 journal + checkpoint 续跑；支持用户取消、会话单飞（同一会话不并行跑两个 run）；
- 并发模型：run 跑在虚拟线程上（工具会阻塞，如 `ask_user` 最长等 5 分钟），进程内信号量限 8 个并发 run；
- 单轮最多 8 次模型请求，LLM 超时 180s，事件上限 2000 条，失联宽限 120s。

**② 上下文工程（1M 窗口 + 压缩）**
- 参考 DSH compaction-basic：窗口 1M；阈值 `floor(min(W×0.8, W−输出预留−65536))`；保留最近 `(W−输出预留)×16%` 原文；
- 只压缩「检查点之后、保留段之前」的消息，一次非流式调用生成结构化检查点（用户目标/已确认事实/已完成/约束），写入 `agent_sessions.summary + summary_upto`；
- 检查点之后的原文继续按原样发送，支持多次压缩合并旧检查点；压缩失败不阻断对话；
- 工具定义按名称排序、系统提示只放稳定内容、当前时间追加到最后一条用户消息末尾，保证前缀可缓存。

**③ 缓存与成本优化（最有含金量的部分）**
- 接入 `stream_options.include_usage`，解析 `prompt_tokens / completion_tokens / prompt_cache_hit_tokens`（兼容 `prompt_tokens_details.cached_tokens`）；
- 按会话累计 `Σhit / Σprompt` 持久化，面板展示「会话累计 + 最近一次」；每条助手消息再单独记录当次 usage，展示消息级命中率（输入 / 命中 / 输出）；
- 用真实 API 验证：同一会话第二轮 2816/3010 = 93.6%，两轮累计 5632/6010 ≈ 93.7%，新会话首轮 93.9%；
- 排查联网搜索场景「缓存命中恒 0」：定位到二阶段重建历史（丢时间注记）、移除 `tools`、注记位置不一致导致前缀失配；同时发现 `tool_choice: 'none'` 会让服务端把 tools 从提示词里整个删掉（输入 354 → 86 tokens），最终采用「复用第一阶段消息快照 + 原样 tools + 搜索结果尾部追加 + 指令约束 + 工具调用兜底重试」，对照实验命中 0 → 256/416。

**④ 工具平台（14 个工具）**
- 基于 Spring AI `@Tool` 注解统一注册，集中目录（`AgentToolCatalog`）聚合，前端展示工具清单与调用卡片；
- 分类：数据查询 3（概览/分页查表/单条详情，只读）、RAG 2（语义检索/素材库状态）、写作 4（一键大纲/作品列表/章节列表/生成章节，自动落库）、任务 2（计划/回写步骤）、提问 1（阻塞等用户选择）、联网 1、下载 1；
- 安全边界：schema 标记的敏感列（API Key 等）从可读列剔除并打码；下载仅 http/https、拒绝本机/内网地址（防 SSRF）、手动重定向 ≤3 跳、单文件 ≤50MB；工具结果/事件文本截断，避免撑爆上下文与前端。

**⑤ 自研流式客户端**
- 不用 Spring AI 的托管 ChatClient，而是自研 OpenAI 兼容 SSE 客户端：解析 `delta / reasoning_content / tool_calls 分片`、usage、错误与取消；
- 首 token 前失败自动重试/退避；首 token 后不重试，避免重复内容；工具调用按 index 累积再一次性执行；
- 与 Spring AI 的分工：只用它的 `@Tool` 注解生成 JSON Schema。

**⑥ 前端 Agent 控制台（Vue 3）**
- 会话列表 / 历史加载 / SSE 实时渲染；工具调用卡、任务清单卡、用户提问卡、大纲生成阶段进度、下载库；
- 上下文占用进度条、会话累计缓存、每条回答缓存命中；模型/温度/思考模式/联网搜索等面板设置。

### 结果（可直接放简历的量化）
- 缓存：第二轮 93.6%，两轮累计 93.7%；搜索回答从 0 提升到可控的非零命中；
- 上下文：1M 窗口下，长会话不再按轮数截断，仅在接近阈值时压缩一次，保留 16% 原文；
- 工具：14 个，7 类能力，写操作自动落库（大纲/章节）；
- 稳定性：SSE 断线重连、进程重启恢复、取消、会话单飞全部实现；
- 规模：Agent 后端约 4.6k 行 Java，控制台约 3.1k 行 TS/Vue，9 个后端单测类；
- 交付：可运行 Web 控制台 + 移动端接入，真实 API 跑通并发布版本。

## 3. 技术难点怎么讲（面试展开点）

### 3.1 断线重连 / 进程重启恢复
- 问题：移动网络/代理会掐断 SSE，长任务不能丢；服务重启后不能把进行中的 run 丢掉。
- 方案：事件落库带 `seq`；前端重连从最后 `seq` 拉增量；run 状态机 + journal/checkpoint；启动恢复扫描未完成 run 续跑；前端「断开但后台在跑」时自动 resume。
- 可讲点：如何避免重复事件、如何区分「正常结束/被掐断/用户取消」。

### 3.2 前缀缓存与 usage
- 问题：长会话每轮输入极大，缓存命中直接决定成本。
- 方案：稳定前缀（system、工具、历史）+ 变化内容后置（时间、压缩摘要、搜索结果尾部）；持久化 usage 做可视化。
- 数据：第二轮 93.6%；缓存只认完整前缀单元，尾部新增内容必 miss，所以「命中率不是越高越好，而是把大段稳定内容放前面」。
- 可讲点：`prompt_cache_hit_tokens` 与 `prompt_tokens_details.cached_tokens` 的兼容；缓存 best-effort、几秒构建、闲置数小时到几天清理。

### 3.3 1M 上下文压缩
- 问题：长会话不能无限塞；按轮数截断会丢关键设定。
- 方案：窗口预算 + 阈值触发 + 结构化检查点 + 保留最近原文；检查点持久化，重启/切换会话仍有效。
- 可讲点：为什么保留 16%、为什么 headroom 取 64K、压缩调用本身怎么避免被统计进对话 usage。

### 3.4 工具安全边界
- 敏感列（schema 标记 + 查询列剔除 + 行级打码）；
- SSRF：只允许 http/https，拒绝本机/内网，手动处理重定向；
- 大小与截断：下载 50MB、分页 50、搜索 8 条/次、事件与预览截断；
- 可讲点：写工具（生成大纲/章节）目前无审批，是下一步要补的 HITL。

### 3.5 搜索两阶段 0 命中排查（推荐重点讲）
- 现象：普通回答缓存 64%～74%，联网搜索回答恒 0；
- 假设：搜索正文太大 → 验证：非搜索轮也小，命中正常，排除；
- 定位：①第二阶段重建历史丢掉时间注记；②第二阶段删掉 tools；③上一轮搜索插入的搜索上下文不进历史；
- 实验：真实 API 小请求对照（第一阶段 354 tokens；旧第二阶段 111/0；新第二阶段 416/256）；
- 额外发现：`tool_choice: 'none'` 会剥离 tools，前缀同样失配，于是改用 auto + 指令约束 + 兜底重试；
- 方法论：从「缓存是前缀单元」出发做对照实验，而不是猜。

## 5. 面试问答准备（12 问）

1. **为什么不用 Spring AI 的 ChatClient 全托管？**
   需要自己控制 SSE 重连、usage、取消、首 token 前重试、工具分片累积；Spring AI 只用来做 `@Tool` schema 生成。
2. **run 恢复怎么做到不重复执行工具？**
   事件/工具调用结果落库，恢复时按 journal 回放；工具执行前有 run 状态/幂等设计（这是后续可加强点，可如实说）。
3. **上下文压缩的阈值怎么定的？**
   参考 DSH 公式与官方 1M 窗口、输出预留、64K headroom；保留 16% 保证最近上下文完整。
4. **缓存命中率怎么算？**
   `prompt_cache_hit_tokens / prompt_tokens`（只算输入）；不是整轮对话，也不是输出。
5. **为什么不是 100%？**
   前缀单元完整匹配、尾部新内容必 miss、缓存 best-effort 且会过期。
6. **会话累计和最近一次有什么区别？**
   累计 `Σhit/Σprompt` 看省钱；最近一次看当前请求；消息级看单条回答。
7. **工具怎么保证安全？**
   敏感列剔除/打码、SSRF 防护、大小限制、结果截断；写操作后续加审批。
8. **ask_user 阻塞线程怎么办？**
   虚拟线程 + 超时 5 分钟 + 取消唤醒；并发上限 8，因此企业化要换成持久化的人工任务队列。
9. **单机还是多机？**
   单机（内存 run/ask 注册表 + 进程内信号量）；如实说明，多实例需要队列与租约。
10. **怎么做测试？**
    9 个后端单测类覆盖上下文预算、run、usage、prompt、工具脱敏、SSRF；前端/移动端另有相关用例；不足是没有 Agent 评测集。
11. **提示词怎么迭代？**
    目前靠人工 + 单测 + 真实 API 对照；下一步做 prompt 版本化与 golden task 评测。
12. **如果给你继续做，优先级？**
    身份租户/RBAC → 写工具审批 → 审计与指标 → 队列化/多实例 → 评测与灰度。

## 6. 简历包装建议

- **标题**不要写「小说 App」，写「AI 创作 Agent 平台（Agent 运行时 + 工具调用 + 长上下文/缓存优化）」，小说只是场景。
- **岗位映射**：
  - LLM 应用 / Agent 工程：突出运行时、工具平台、上下文工程、缓存与成本；
  - Java 后端：突出 Spring Boot / Spring AI / SSE / 虚拟线程 / run 状态机 / MySQL；
  - 全栈：后端 + Vue 控制台 + 移动端接入。
- **可迁移能力**：Agent 运行时、工具安全边界、上下文压缩、前缀缓存优化、流式与断线恢复——这些和具体业务无关，面试官更看重。
- **别写**：高并发、多租户、生产级大规模、SLA；当前是单机/单租户、可信环境。
- **可展示**：控制台截图（工具调用卡、计划任务、提问卡、缓存命中条、压缩提示），两份 verification 报告作为数据证据。

## 7. 如实边界与下一步（面试被追问时的回答）

- 单机部署，进程内并发 8；run/ask 注册表在内存，重启恢复是单机语义；
- 身份是客户端自报 `x-device-id`，只有可选全局 API Token；无用户/角色/租户；
- 写工具（生成大纲/章节）无人工审批、无回滚；
- 无 Prometheus/OTel 指标与独立审计日志；
- RAG 素材库是服务端全局索引，未按租户隔离；
- 无 CI/CD、无 Flyway、无 Agent 评测集。

下一步规划（可讲）：SSO + 租户/RBAC → 写工具审批 + 审计 → 指标/告警/成本预算 → 任务队列与多实例 → 评测集与 prompt 版本化。
