## 1. 一页简历版（可直接粘贴）

**AI 小说创作 Agent 平台**（个人项目 / 独立开发，2026.10 – 2026.11）
*Java 21 · Spring Boot 3.4 · Spring AI 1.0.9 · 自研 OpenAI 兼容流式客户端 · Vue 3 + TypeScript · SSE · MySQL · Elasticsearch · DeepSeek · Qwen3.7 Embedding*

- **Function Calling**：基于 Spring AI `@Tool` 注解统一注册 **14 个工具**（数据查询 / RAG 检索 / 大纲与章节生成 / 任务计划 / 向用户提问 / 联网搜索 / 下载），自研 OpenAI 兼容流式客户端，支持工具调用分片累积、`reasoning_content` 回传、首 token 前重试、取消检查与 **单轮最多 8 次工具循环**；工具调用/结果通过 SSE 事件实时渲染成卡片。
- **对话中断续跑**：SSE 事件带自增 `seq`，run 与浏览器连接解耦；断网/刷新/多标签页通过 `afterSeq` 重放事件并重新 attach，120 秒无人接管才取消；进程重启后恢复已生成正文、工具卡片和任务计划，并标记 `interrupted`，用户发「继续」即可接着做；任务步骤、工具状态、usage 全部落库。
- **RAG 检索工程**：搭建 `txt → 格式检测/结构化 → 情节弧窗口 → DeepSeek 并行提炼 → 跨窗口去重 → Qwen embedding → Elasticsearch kNN` 的完整导入与检索链路；提供 `search_rag` / `rag_status` 两个 Agent 工具，支持按标签过滤、按作品覆盖、导入任务实时进度。
- **RAG 拆分策略**：把原来的「8000 字贪心装块」升级为「格式检测 → 段落/章节结构化 → 按章组情节弧窗口（带重叠前缀）→ 并行提炼（带续接状态）→ 合并去重」；《三国演义》60.8 万字 → 120 章 → **64 个窗口、0 章被切断**（旧方案 78 块、77/120 章被切），6 窗口并行提炼 65 秒完成。

## 2. 详细版（面试展开）

### 2.1 Agent Function Calling

**注册与协议**
- 用 Spring AI `@Tool(name/description/@ToolParam)` 声明 14 个工具，`AgentToolCatalog` 反射聚合成工具清单，再转成 OpenAI `tools` JSON Schema；联网搜索关闭时该工具不注册给模型。
- 工具分 7 类：数据只读 3、RAG 2、写作（大纲/章节）4、任务 2、提问 1、联网 1、下载 1。写操作（生成大纲/章节）自动落库并返回 id；读操作做敏感列脱敏、分页上限、SSRF 防护、下载 50MB 上限。
- 工具定义按名称排序、系统提示只放稳定内容、时间注记追加到最后一条用户消息末尾——保证多轮请求的 **prompt 前缀稳定**，命中提供方缓存。

**自研流式客户端（为什么不用全托管 SDK）**
- 供应商是 OpenAI 兼容协议，但需要自己控制：SSE 解析、`usage` 统计、取消、首 token 前重试、工具调用分片合并。
- 工具调用以 `index` 累积 `delta.tool_calls` 的 id/name/arguments 分片，结束后一次性执行；执行结果以 `role=tool + tool_call_id` 回填消息链。
- 思考模式下把 `reasoning_content` 一并回传，避免工具回合 400；未知工具/工具异常转成文本结果交回模型，不让整轮失败。
- 工具循环上限 8 轮；轮次用尽后再发一次「不带工具」的收尾请求，让模型把已查到/已生成的内容讲清楚，而不是整轮作废。
- 重试只针对首 token 前（429/5xx），一旦已经向前端推过内容就不重试，避免重复输出。
- 所有工具调用通过 `tool_call / tool_result / tool_error` 事件推给前端渲染成卡片，长结果截断到 8k 字符，前端可展开查看参数和摘要。

**控制面**
- 单实例同时运行 run 上限 8；同一会话单飞，避免两个 run 互相踩历史；`ask_user`、章节生成等阻塞工具跑在虚拟线程上，不占平台线程。
- 取消：模型流、工具执行前后都检查 `run.cancelled()`；取消后把仍在 running 的工具卡收尾为 error、等待中的 ask 收尾为 timeout，持久化状态为 cancelled。

### 2.2 对话中断时，任务和工具调用怎么继续

| 场景 | 行为 |
|---|---|
| 浏览器断网 / 刷新 / 多标签页 | run 在服务端独立继续，事件带 `seq` 缓冲；重连 `GET /runs/{id}/stream?after=lastSeq` 从断点重放并继续跟随；页面刷新通过 `GET /runs/active` 找到本设备未结束的 run 并接管（先补会话历史，再接实时流）。工具调用继续执行，重连后能看到 `tool_result`。 |
| 断开后一直没人回来 | 断连宽限期 **120 秒**；超时仍无客户端 attach 才取消 run，避免用户关页面后一直烧 token。attach 期间每 15 秒 ping 保活。 |
| 服务进程重启 | 模型的 HTTP 流无法跨进程续传，所以恢复的是「已产出的内容 + 中断状态」：启动时扫描 `running` run，把 `text_so_far + parts_json` 补成一条 `interrupted` 历史消息（正文、工具卡都在），任务计划标记 interrupted；用户看到半截回答后发「继续」接着做。**工具不会自动重放**，这是有意的取舍（避免重复副作用），也是后续要补幂等键/持久化步骤日志的地方。 |
| 用户主动停止 | 取消信号贯穿模型流与工具执行；`markFinished` 统一收尾未返回的工具卡 / 未回答的提问，保证历史消息不会永远“转圈”。 |
| 提问 / 任务计划 | `agent_tasks` 持久化任务与每一步状态，刷新后仍可见；`ask_user` 阻塞等待用户选择（最长 5 分钟），超时让模型按默认方案继续。 |

**一致性设计**
- `AgentJournal` 异步 checkpoint 到 MySQL：工具/任务/提问等非增量事件立即写，token 增量按 800ms 节流；同一 run 只排队一个在途快照，DB 抖动也不会堆积。
- 事件同时写入 run 内存缓冲和消息 parts 时间线；`parts_json` 持久化后，刷新/重启都能恢复“文字 + 工具卡 + 提问卡 + 任务”的完整时间线。
- 前端 `resume()` 用 `afterSeq` 重放，只在收到 `done/cancelled/error` 才标完成；连接断了没收到终止事件就标记「连接中断，内容可能不完整」，不会误报完成。

### 2.3 RAG 检索工程

- **导入链路**：`txt 解码（UTF-8/GB18030）→ 格式检测 → 段落/章节结构化 → 情节弧窗口 → DeepSeek 并行提炼 → 跨窗口去重 → 百炼 embedding → Elasticsearch 写入`。
- **存储结构**：每个情节 = `title / plot / excerpt / tags / characters / sceneType / emotion / reusable / embedding / book / createdAt`；索引 `novel_rag_scenes`，dense_vector `dims=1024, cosine`，IK 分词不可用时自动回退 `standard`；同一作品重导按 `book` 先删除再全量覆盖。
- **检索**：查询文本用同一个 embedding 模型（qwen3.7-text-embedding-flash，1024 维）向量化，走 ES kNN，`k` 最大 30、`num_candidates=max(50,k*10)`，可按 tags 过滤；实测「桃园结义 三兄弟」对《三国演义》素材 top1 score 0.826。
- **Agent 接入**：`search_rag`（语义检索素材，写章节前找参考）、`rag_status`（索引/作品/标签状态）作为 Agent 工具，模型可以在写作前主动检索参考情节。
- **任务化**：导入是后台任务，窗口状态、每个窗口的 DeepSeek 原始输出、进度都可在页面轮询查看；切页后通过 `/jobs` 恢复。

### 2.4 RAG 拆分策略（重点）

**旧方案的问题**
- 按「空行分段 + 8000 字贪心装块」；《三国演义》600k 字被切成 78 块，块边界不按章节，实测 **77/120 回被切到两个块**，模型容易拿到半截剧情；txt 格式不统一时还会退化为按字符硬切。

**新方案（五步）**
1. **格式检测**：空行分段 / 单换行分段（一行一段的网文）/ 整篇无换行三档；超长段落先按句末标点切，保证窗口不从半句话开始。
2. **章节识别**：`第X回/章/节`、`Chapter N`、数字标题三套候选，按命中数量 + 编号单调性选择；识别不到章节时退化为按段落组窗口，不假设 txt 一定有章节。
3. **情节弧窗口**：识别到章节时**按章组窗口、不跨章切**；目标 12,000 字，相邻窗口带上一个窗口末尾 1,500 字的「重叠前缀」；单章超过 2 倍窗口时再按句末切子窗口；窗口数上限 400，防超长文本失控。
4. **并行提炼 + 续接状态**：按 `concurrency`（默认 4）分批并行调用 DeepSeek；每批结束后把最后一条情节摘要作为下一批的「续接状态」塞进 prompt，明确要求不重复上一批、不补全不完整情节；窗口本身的重叠前缀提供原文级连续性。
5. **合并去重**：相邻窗口按标题相似度 + plot 字符二元组 Jaccard 相似度去重，`mergedCount` 记录合并数量，避免重叠区同一情节入库两次。

**效果与取舍**
- 《三国演义》实测：120 章 → **64 个窗口**，窗口 6.9k–13.4k 字，**0 章被切断**；旧方案 78 块、77 章被切。
- 30k 字样例：解析出 3 窗口；改 8000 字/800 重叠后重划分为 6 窗口；并行 3 路提炼 6 个窗口 **65 秒**完成（串行约为 3 倍时间），每窗口原始输出 3k–8k 字符全部可查。
- 取舍：重叠会让 token 增加约 10%~20%，换来跨窗口情节完整；窗口太大会挤占输出预算，12k 是实测平衡点；章节识别有误时自动退回段落窗口，不会因格式差异直接失败。
- **两阶段导入**：默认「分块完成后手动开始提炼」——先让用户预览每个窗口的原文/章节范围，可改窗口字数、重叠、并行数后重新划分，确认后再消耗 LLM 提炼；关闭开关则解析完自动开始。

## 3. 面试高频问答

1. **Function calling 为什么不用 Spring AI 全托管？**
   需要自控 SSE 解析、usage、取消、首 token 前重试和工具分片累积；Spring AI 只用来声明 `@Tool` schema。
2. **工具调用的参数是流式的，怎么保证完整？**
   按 `delta.tool_calls[].index` 累积 id/name/arguments 分片，流结束后统一 JSON 解析执行；解析失败转成错误文本回给模型。
3. **思考模式 + 工具为什么容易 400？**
   带 `tools` 的请求必须回传历史 `reasoning_content`；自研客户端把 reasoning 一并写回 assistant 消息。
4. **断网后凭什么继续跑？**
   run 生命周期独立于 HTTP 连接，事件进内存缓冲并带 seq；客户端只是 attach 消费者，重连用 afterSeq 重放。
5. **为什么 120 秒没人接管要取消？**
   避免用户关页面后无限烧 token；重新打开页面会先查 active runs，能接上的都会接上。
6. **进程重启算“续跑”吗？**
   不算执行续跑，算状态恢复：已生成内容 + 工具卡 + 任务计划保留，标记 interrupted，用户「继续」；模型流不能跨进程续传，工具也不自动重放（避免重复副作用）。
7. **RAG 为什么不按 8000 字固定切？**
   章节/情节弧会被切断；而且不同 txt 格式差异大，固定字符切不可靠。改成格式检测 + 章节结构化 + 带重叠的窗口。
8. **一个情节跨好几章怎么办？**
   窗口按章成组、相邻窗口重叠 1.5k 字，并提供续接状态；跨窗口的完整情节至少有一个窗口能完整看到，重复部分事后去重。
9. **怎么控制成本和速度？**
   并行提炼（默认 4 路）、embedding 批量 8 条最多 4 路、窗口 12k 平衡输出预算；并行 6 窗口约 65 秒。
10. **这套拆分还有什么不足？**
    章节识别是启发式；去重只用文本相似度；服务重启会丢进行中的导入任务；这些是后续要补的点（见边界）。

## 5. 简历包装建议

- 标题写 **「AI Agent 平台（Function Calling + 中断续跑 + RAG）」**，小说只是落地场景，面试官关注的是可迁移能力。
- 三条主线按岗位侧重点排序：
  - Agent 工程：先 Function Calling，再中断续跑，再 RAG；
  - LLM 应用/算法工程：先 RAG 拆分/检索，再 Function Calling；
  - Java 后端：先中断续跑/事件流/持久化，再工具治理。
- 可展示：工具调用卡片、任务清单、提问卡、窗口预览 + 每个窗口的 DeepSeek 原始输出、切页恢复进度的截图。
- 不要写“生产级多租户/高并发/SLA”；写“单机、单租户、可信环境，8 并发”。

## 6. 如实边界（被追问时主动说）

- 进程重启是**状态恢复 + 用户「继续」**，不是模型流/工具执行的原位续跑；缺持久化步骤日志与工具幂等键，这是下一步。
- 前端断线重放依赖 run 内存缓冲，事件超过 2000 条会被截断（超长回答的早期事件可能丢），生产化应改为持久化事件日志。
- 工具权限目前只有「联网搜索开关」，没有按角色/租户的工具白名单与写操作审批。
- RAG 的章节识别/去重是启发式：识别不到章节会退回段落窗口；去重只比较相邻窗口，复杂重复可能漏。
- 导入任务在内存里，服务重启会丢进行中的任务；RAG 索引是服务端全局的，没有按设备/租户隔离。
